# Todo

- [x] **Carve out the eligible-column pool.** Key guessing begins by listing the identified, comparable column pairs whose values contain no null or `NaN` on either side, in old-side column order. A column with any invalid value can never take part in any candidate of any width, so it leaves before the lattice exists. This pass reuses the canonicalization and digest machinery `guess_key` already runs per column, so the pool costs what the single-column scan costs today.
- [x] **Build the per-side uniqueness index.** Each eligible column's duplicate structure on each side, in position-list form (the rows sharing each duplicated value, equality confirmed inside digest buckets as everywhere else). A combination's uniqueness is validated by intersecting position lists, which shrink monotonically with width, so validation cost concentrates exactly where duplication does.
- [x] **Implement the bounded lattice search.** Breadth-first by width from 1 to `key_width`, extending only combinations that failed uniqueness on at least one side, generated in prefix order over old-side column indexes so every combination is enumerated once, deterministically. Two prunes: minimality — no superset of an eligible candidate is ever generated, because a superset shares at most as many tuples and loses the fewer-columns tie-break by construction — and agree sets, HyUCC's row-based half: the first violating row pair a validation finds yields the full set of eligible columns those two rows agree on, and any later combination that is a subset of a recorded agree set is non-unique on that side without validation.
- [x] **Unify the ranking across widths.** One candidate pool: most shared tuples, then fewer columns, then freedom from fanout, then old-side column order. Width-1 candidates keep today's rules exactly (unique in old, bounded new-side fanout tolerated); a wider candidate must be unique in both sides and share at least one tuple, so the fanout tie-break can only ever separate width-1 candidates and today's single-column behavior is preserved verbatim where a single column wins.
- [x] **Meter the search.** Two new fields on `Budgets`: `key_rows: RowBudget` (default `PerCell(2)`) charging each uniqueness validation and each shared-tuple measurement the rows it actually reads, and `key_candidates: usize` (4096) capping the combinations admitted to the lattice. Exhaustion is sticky and the meter's order is the enumeration order, so the stranded candidates are one deterministic tail. `key_width` (default 4) is the search's definition rather than its budget: exhausting the lattice under the width cap is a complete search of the bounded space and reports nothing. *Decided during implementation:* the proportional form resolves with a floor of 65 536 rows, because the lattice's cost scales with column combinations where cells scale with rows, and a small wide table was otherwise refused a search that costs almost nothing in absolute terms; the absolute `Rows` form stays floorless so tests meter exactly.
- [x] **Report exhaustion.** A new `IncompleteStage::KeyGuess`, first in the fixed order (key resolution precedes renames in the pipeline story), rendered as `incomplete_key_guess()` in the problems block. On exhaustion the best eligible candidate examined so far wins — a useful partial result — and the fallback chain below it is unchanged. Reconsideration's second pass runs under fresh counters, and the diff reports the incompleteness of the pass it kept, both as the design already specifies.
- [x] **Integrate with reconsideration.** `guess_key`'s `excluded` becomes a list of retracted candidates, each an exact column-set: a retracted compound is never guessed again, while its individual columns stay available to other combinations. # Goal

Close issue #4: extend key guessing beyond individual columns using a unique-column-combination search in the HyUCC family, so a table whose identity is `(group, id)` gets a semantic diff instead of the positional fallback. A candidate combination must contain no missing values and be unique in both `old` and `new`; candidates rank by shared key tuples, then fewer columns, then column order; the guess reports the same normalized overlap single-column guessing reports and stays visible and overrideable; no fanout is ever inferred from a guessed compound key; and the search runs under counted bounds on width, candidate count, and work, returning a useful partial result and reporting itself non-exhaustive when a budget binds.

# Design notes

**Why the unified ranking is safe.** Shared-tuple count is monotone under projection when the subset is unique in `old`: every shared wider tuple projects to a shared narrower one, so a superset of an eligible candidate shares at most as many tuples and then loses the fewer-columns tie-break. That is what makes minimality pruning lossless rather than heuristic, and it is why the issue's ranking (evidence first, parsimony second) composes with today's single-column rule without a special case: adding "fewer columns" between shared count and fanout-freedom changes no comparison between two width-1 candidates.

**Why width is not a budget.** `agreement_rows` set the precedent: completing inference over a fixed, documented horizon is not exhaustion. `key_width` defines the space the search promises to cover; `key_rows` and `key_candidates` bound the work of covering it. Only the latter two can strand generated-but-unexamined candidates, so only they report `incomplete_key_guess()`.

**Why both sides must be unique.** For width 1 the design tolerates bounded new-side fanout because a single column duplicated by a join is still the best evidence available. A compound candidate has an alternative the single column lacks: one more component. Requiring uniqueness in both sides keeps every compound guess incapable of fanout by construction, which is how "do not infer fanout from a guessed compound key" is enforced without a check downstream — there is no duplicated group for row matching to find.

**Memory bound.** Position lists are held only for the current lattice frontier, whose size `key_candidates` caps, and each list is at most one side's row count; agree sets are capped by the same candidate budget since each validation records at most one. Memory is therefore bounded by the two counted budgets and needs no third knob.

# Verification

* A table where no single column qualifies and `(group, id)` is unique both sides: guessed compound, correct `table_key` line, correct overlap, rows matched semantically.
* Ranking: a compound sharing more tuples beats a single column sharing fewer; a single column ties a compound on shared tuples and wins by fewer columns, a fanning single column included, pinning the issue's ordering; equal-width ties fall to fanout-freedom then column order as today.
* Eligibility: a column with one null or `NaN` anywhere joins no candidate of any width; a compound unique in `old` but duplicated in `new` is ineligible and produces no fanout event; a compound sharing zero tuples is ineligible.
* Budgets: `key_candidates` and `key_rows` each forced to bind via `RowBudget::Rows`/small absolutes, returning the best already-examined candidate with `incomplete_key_guess()` in the problems block and byte-identical repeats; a `key_width` lattice completed under budget reports nothing.
* Reconsideration: a retracted compound guess is excluded as a set and its columns recombine into the next candidate; a renamed key column recovered by pass-one inference becomes a component on pass two.
* Existing behavior: every current fixture where a single column is guessed today still resolves identically unless a compound now outranks it on shared tuples, and each such change is read and justified in the README diff.

# Definition of done
